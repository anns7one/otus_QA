# Генерация тест-кейсов и оценка их качества

Итоговый проект курса OTUS «AI в тестировании», вариант 1.

Система поднимает Ollama в Docker и генерирует тест-кейсы по требованию. Каждый кейс содержит описание, ожидаемый результат и граничные значения. Обученная на PyTorch NLP-модель оценивает каждый сценарий по четырём метрикам. Результаты сохраняются в JSON, визуализируются графиками matplotlib и seaborn и сводятся в Markdown-отчёт.

## Как это работает

```
input/requirement.md
   │
   ├─ analyze_requirement.py review    анализ требования: находки → автор правит поля или принимает риски;
   │                                   модель разбирает правила полей, автор подтверждает их
   │                                   → output/requirement_review.json (с SHA-256 требования)
   │
   └─ main.py run
        ├─ generate_cases.py           Ollama (qwen2.5:7b) пишет кейсы: 6 обязательных проверок на каждое поле
        │                              + 6 свободных; код исправляет исходы граничных значений по правилам полей
        ├─ quality_model.py            обучение модели качества на data/ и оценка кейсов
        └─ report.py                   output/results.json, output/plots/*.png, output/report.md

main.py build-dataset → build_dataset.py   Ollama генерирует датасет data/requirements.json + data/scenarios.jsonl
```

Главный принцип: **код гарантирует, модель формулирует**.

- **Что делает модель.** Пишет тексты: кейсы и находки анализатора. Распознаёт, какие правила записаны в требовании.
- **Что делает код.** Задаёт, какие проверки обязательны. Проверяет, что цитаты дословные. Вычисляет исход для каждого граничного значения (длина, допустимые символы, маска). Считает покрытие.
- **Что делает человек.** Подтверждает разобранные правила полей. Ollama на GPU не даёт одинакового ответа даже при `temperature=0`, поэтому без подтверждения нельзя.

## Метрики качества сценария

| Метрика | Что значит «хорошо» |
|---|---|
| Читаемость | Понятный язык, одно действие в шаге, нет двусмысленности |
| Чёткость целей | Из названия и описания ясно, что и зачем проверяется |
| Покрытие сценариев | Учтены ограничения требования, есть граничные значения |
| Согласованность | Описание, шаги и ожидаемый результат не противоречат друг другу |

- **Оценка сценария:** среднее по четырём метрикам, от 0 до 1.
- **Качество:** «Высокое» при оценке от 0.75, «Среднее» от 0.5, иначе «Низкое».
- **Успешный сценарий:** каждая из четырёх метрик не ниже 0.5.

## Модель

- **Векторы текста.** Каждая часть сценария и требование превращаются в векторы замороженным энкодером `paraphrase-multilingual-MiniLM-L12-v2`. Частей четыре: название с описанием, шаги, ожидаемый результат, граничные значения. Их кодируем по отдельности, потому что энкодер обрезает длинный текст.
- **Признаки.** Векторы частей и косинусные близости между частями и с требованием.
- **Сеть.** На PyTorch: `Linear → ReLU → Dropout → Linear`, 4 выхода, `BCEWithLogitsLoss` (multi-label), Adam, early stopping по валидации.
- **Деление выборки.** Train, validation и test делятся **по требованиям**, а не по сценариям, чтобы не было утечки данных.
- **Сравнение с базовыми моделями** на test: «самый частый класс» и логистическая регрессия только по длине текста. Если модель не лучше «длины», значит, она выучила объём текста, а не качество.

## Датасет

`build_dataset.py` генерирует 24 требования из разных предметных областей и по 8 сценариев на каждое:

| Вид | Сколько | Метки [чит, цель, покр, согл] |
|---|---|---|
| Хороший | 3 | [1, 1, 1, 1] |
| Испорчена одна метрика | 4 | одна 0, остальные 1 |
| Плохой целиком | 1 | [0, 0, 0, 0] |

Метки — это то, что мы просили сгенерировать (слабая разметка, weak supervision). Модель просят сохранять объём текста, чтобы плохие сценарии не отличались одной длиной. Каждый сценарий сохраняется сразу, поэтому после сбоя генерация продолжается с того же места.

## Запуск

Нужны Python 3.11+, Docker Desktop и, по желанию, GPU NVIDIA.

```
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python analyze_requirement.py review   # проверить требование и подтвердить правила полей
python main.py run                     # кейсы → обучение → оценка → отчёт
python main.py run --reuse-cases       # то же, но без повторной генерации кейсов
python main.py build-dataset           # заново сгенерировать датасет (долго, ~40 мин)
python -m pytest tests                 # тесты, Ollama не нужна
```

Ollama запускается сама через `docker compose` на порту `127.0.0.1:11400`. Порт выбран потому, что Windows резервирует диапазон 11435–11534. Модель `qwen2.5:7b` скачивается автоматически, если её ещё нет.

## Результаты

**Датасет:** 24 требования, 175 сценариев (17 отброшены как дубли). Разбиение по требованиям: train 17 требований (122 сценария), validation 4 (30), test 3 (23).

**Модель качества на test.** Требования из test модель не видела при обучении. Метрики ROC-AUC и macro-F1 при пороге 0.35: порог подобран на validation. Хороших меток около 85%, поэтому обычный F1 и accuracy ничего не показывают: модель «всё хорошо» получила бы F1 ≈ 0.85.

| Метрика | Модель, AUC / F1 | Самый частый класс, AUC / F1 | Только длина, AUC / F1 |
|---|---|---|---|
| Читаемость | 0.67 / 0.62 | 0.50 / 0.42 | 0.72 / 0.42 |
| Чёткость целей | 0.68 / 0.58 | 0.50 / 0.44 | 0.66 / 0.44 |
| Покрытие | 0.75 / 0.73 | 0.50 / 0.42 | 0.37 / 0.42 |
| Согласованность | 0.78 / 0.70 | 0.50 / 0.42 | 0.50 / 0.42 |

- Модель обходит обе базовые модели по macro-F1 на всех четырёх метриках, а по ROC-AUC — на трёх из четырёх.
- По читаемости длина текста сильнее, ROC-AUC 0.72. Плохо читаемые сценарии в датасете в среднем длиннее: 905 символов против 797 у хороших. Здесь длина действительно подсказывает ответ.
- В test всего 3 требования и 23 сценария, поэтому цифры шумные.

**Кейсы для REQ-01:** 30 кейсов, покрыто 24 из 24 обязательных проверок. Код исправил исходы граничных значений в 6 кейсах.

Ручная проверка нашла 4 кейса с ошибками в устройстве. Модель отметила неуспешными ровно 3 кейса, все три — из этих четырёх:

| Кейс | Ошибка | Отмечен моделью |
|---|---|---|
| TC-002 | Две проверки в одном кейсе; в шаге «50 символов» у строки из 52 | да |
| TC-029 | Придумано правило «минимум 8 символов» для Имени | да |
| TC-030 | «Иванов Иван Иванович»: два пробела внутри, а ожидается успех | да |
| TC-026 | Название про пароль без заглавной буквы и цифры, а в шагах пустая строка | нет |

На реальных кейсах это 3 найденных из 4 и ни одной ложной тревоги. Выборка маленькая, это иллюстрация, а не измерение.

**История ошибок генератора.**

| Версия | Кейсов с логическими ошибками |
|---|---|
| Первая генерация | 11 из 29 |
| После вычисления исходов кодом | ~4 из 29 |
| После классификации свободных кейсов и отдельной проверки длины для маски | 4 из 30 |

В последней версии все 4 ошибки — в устройстве кейса, исход граничных значений везде верный.

Отчёт: `output/report.md`, данные: `output/results.json`, графики: `output/plots/`, история обучения: `output/training_metrics.json`.

## Ограничения

- **Анализатор требований.** На контрольном наборе из 9 требований (46 известных дефектов) он находит 48–52% дефектов (recall). Цель 70% на qwen2.5:7b не достигнута. Точность (precision) не измерялась, на хорошо описанном требовании большая часть находок — шум. Поэтому находки только подсказка автору, решение принимает человек.
- **Генератор.** Ошибки в устройстве кейса код не исправляет: несколько проверок в одном кейсе, придуманное правило в названии, шаги не совпадают с названием.
  - Исход «принимается» код ставит только в кейсах, которые проверяют формат значения: это обязательные кейсы и свободные кейсы, которые модель отнесла к формату. В остальных кейсах значение может отклоняться по другим правилам, например из-за уникальности.
  - Для поля с маской проверка длины — это «на одну цифру больше, чем вмещает маска». Строку из 1000 символов модель на таком поле зацикливала. Исход для лишней цифры — «не задано»: требование этого не описывает.
- **Метки датасета.** Это намерение при генерации, а не ручная разметка. Сгенерированный сценарий может не содержать заказанного недостатка.
