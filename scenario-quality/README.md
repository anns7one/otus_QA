# Генерация тест-кейсов и оценка их качества

Итоговый проект курса OTUS «AI в тестировании», вариант 1.

Система поднимает Ollama в Docker и генерирует тест-кейсы по требованию. Каждый кейс содержит описание, ожидаемый результат и граничные значения. Обученная на PyTorch NLP-модель оценивает каждый сценарий по четырём метрикам. Результаты сохраняются в JSON, визуализируются графиками matplotlib и seaborn и сводятся в Markdown-отчёт.

## Как это работает

```
input/requirement.md
   │
   ├─ analyze_requirement.py review    анализ требования: находки → автор правит поля или принимает риски;
   │                                   модель разбирает правила полей, автор подтверждает их
   │                                   → output/requirement_review.json (с SHA-256 требования)
   │
   └─ main.py run
        ├─ generate_cases.py           Ollama (qwen2.5:7b) пишет кейсы: 6 обязательных проверок на каждое поле
        │                              + 6 свободных; код исправляет исходы граничных значений по правилам полей
        ├─ quality_model.py            обучение модели качества на data/ и оценка кейсов
        └─ report.py                   output/results.json, output/plots/*.png, output/report.md

main.py build-dataset → build_dataset.py   Ollama генерирует датасет data/train_requirements.json + data/train_scenarios.jsonl
```

Главный принцип: **код гарантирует, модель формулирует**.

- **Что делает модель.** Пишет тексты: кейсы и находки анализатора. Распознаёт, какие правила записаны в требовании.
- **Что делает код.** Задаёт, какие проверки обязательны. Проверяет, что цитаты дословные. Вычисляет исход для каждого граничного значения (длина, допустимые символы, маска). Считает покрытие.
- **Что делает человек.** Подтверждает разобранные правила полей. Ollama на GPU не даёт одинакового ответа даже при `temperature=0`, поэтому без подтверждения нельзя.

## Три набора требований

Тест-кейсы генерируются по одному требованию — `input/requirement.md`. Два других набора не относятся к тестируемому продукту: на одном учится модель качества, на другом измеряется анализатор.

| Где | Что это | Сколько | Кто читает | Зачем |
|---|---|---|---|---|
| `input/requirement.md` | Требование, которое тестируем (форма регистрации) | 1 | `analyze_requirement.py review`, `main.py run` | По нему генерируются кейсы и строится отчёт |
| `data/train_requirements.json` + `data/train_scenarios.jsonl` | Учебные требования и сценарии | 24 и 156 | `build_dataset.py`, `quality_model.py` | На них учится модель качества. Одного требования мало: модель запомнила бы форму, а не научилась отличать хороший кейс от плохого |
| `data/analyzer_golden/REQ-*.md` + `defects.json` | Эталонные требования с известными дефектами | 9 | `analyze_requirement.py evaluate` | Ключ ответов для замера recall анализатора |
| `data/gold.jsonl` | Независимая разметка 40 учебных сценариев | 40 на разметчика | `quality_model.py` | Проверка, насколько верны метки учебных сценариев |

## Метрики качества сценария

| Метрика | Что значит «хорошо» |
|---|---|
| Читаемость | Понятный язык, одно действие в шаге, нет двусмысленности |
| Чёткость целей | Из названия и описания ясно, что и зачем проверяется |
| Покрытие сценариев | Учтены ограничения требования, есть граничные значения |
| Согласованность | Описание, шаги и ожидаемый результат не противоречат друг другу |

- **Оценка сценария:** среднее по четырём метрикам, от 0 до 1.
- **Качество:** «Высокое» при оценке от 0.75, «Среднее» от 0.5, иначе «Низкое».
- **Успешный сценарий:** каждая из четырёх метрик не ниже 0.5.

## Модель

- **Векторы текста.** Каждая часть сценария и требование превращаются в векторы замороженным энкодером `paraphrase-multilingual-MiniLM-L12-v2`. Частей четыре: название с описанием, шаги, ожидаемый результат, граничные значения. Их кодируем по отдельности, потому что энкодер обрезает длинный текст.
- **Признаки.** Векторы частей и косинусные близости между частями и с требованием.
- **Сеть.** На PyTorch: `Linear → ReLU → Dropout → Linear`, 4 выхода, `BCEWithLogitsLoss` (multi-label), Adam, early stopping по валидации.
- **Деление выборки.** Train, validation и test делятся **по требованиям**, а не по сценариям, чтобы не было утечки данных.
- **Сравнение с базовыми моделями** на test: «самый частый класс» и логистическая регрессия только по длине текста. Если модель не лучше «длины», значит, она выучила объём текста, а не качество.

## Датасет

`build_dataset.py` генерирует 24 учебных требования из предметной области тестируемой формы (регистрация, авторизация, восстановление пароля, отдельные поля, уникальность, обязательные поля) и по 8 сценариев на каждое:

| Вид | Сколько | Метки [чит, цель, покр, согл] |
|---|---|---|
| Хороший | 3 | [1, 1, 1, 1] |
| Испорчена одна метрика | 4 | одна 0, остальные 1 |
| Плохой целиком | 1 | [0, 0, 0, 0] |

Метки — это то, что мы просили сгенерировать (слабая разметка, weak supervision). Модель просят сохранять объём текста, чтобы плохие сценарии не отличались одной длиной. Каждый сценарий сохраняется сразу, поэтому после сбоя генерация продолжается с того же места.

## Запуск

Нужны Python 3.11+, Docker Desktop и, по желанию, GPU NVIDIA.

```
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python analyze_requirement.py review   # проверить требование и подтвердить правила полей
python main.py run                     # кейсы → обучение → оценка → отчёт
python main.py run --reuse-cases       # то же, но без повторной генерации кейсов
python main.py build-dataset           # заново сгенерировать датасет (долго, ~20 мин)
python main.py label-gold              # разметить 40 сценариев для проверки меток (текущая разметка в data/gold.jsonl)
python -m pytest tests                 # тесты, Ollama не нужна
```

Ollama запускается сама через `docker compose` на порту `127.0.0.1:11400`. Порт выбран потому, что Windows резервирует диапазон 11435–11534. Модель `qwen2.5:7b` скачивается автоматически, если её ещё нет.

## Результаты

**Датасет:** 24 требования, 156 сценариев (из 192 заказанных: дубли и невалидные ответы отброшены). Разбиение по требованиям: train 17 требований (112 сценариев), validation 4 (26), test 3 (18).

**Модель качества на test.** Требования из test модель не видела при обучении. Метрики ROC-AUC и macro-F1 при пороге 0.60: порог подобран на validation. Хороших меток по каждой метрике около 78%, поэтому обычный F1 и accuracy ничего не показывают: модель «всё хорошо» получила бы F1 ≈ 0.88.

| Метрика | Модель, AUC / F1 | Самый частый класс, AUC / F1 | Только длина, AUC / F1 |
|---|---|---|---|
| Читаемость | 0.96 / 0.91 | 0.50 / 0.44 | 0.55 / 0.44 |
| Чёткость целей | 0.71 / 0.63 | 0.50 / 0.44 | 0.54 / 0.44 |
| Покрытие | 0.88 / 0.73 | 0.50 / 0.44 | 0.73 / 0.44 |
| Согласованность | 0.64 / 0.58 | 0.50 / 0.44 | 0.50 / 0.45 |

В test всего 3 требования и 18 сценариев, поэтому одно разбиение даёт шумные цифры. Надёжнее кросс-валидация ниже.

**Кросс-валидация по требованиям** (`GroupKFold`, 5 разбиений, ROC-AUC, среднее ± стандартное отклонение). Каждое требование ровно один раз попадает в test. Порог и раннюю остановку подбираем на validation внутри обучающей части.

| Метрика | Модель | Самый частый класс | Только длина |
|---|---|---|---|
| Читаемость | **0.78 ± 0.09** | 0.50 | 0.48 ± 0.03 |
| Чёткость целей | **0.74 ± 0.08** | 0.50 | 0.60 ± 0.07 |
| Покрытие | **0.80 ± 0.12** | 0.50 | 0.65 ± 0.08 |
| Согласованность | **0.81 ± 0.07** | 0.50 | 0.76 ± 0.07 |

- По всем четырём метрикам модель обходит обе базовые модели.
- Слабее всего модель различает цель: 0.74. По согласованности «только длина» близка к модели (0.76 против 0.81): испорченные по согласованности сценарии отличаются и по длине. Покрытие нестабильно между разбиениями: ± 0.12.
- Подробности по каждому разбиению лежат в `output/training_metrics.json`, ключ `cross_validation`.

**Проверка меток датасета независимой разметкой** (`data/gold.jsonl`).

Выборка — 40 сценариев: 15 хороших и по 5 каждого испорченного вида. Разметка слепая: разметчик не видит ни вида сценария, ни меток. Кто размечал, записано в поле `annotator`:

- **anna** — человек, 15 сценариев (`python main.py label-gold`);
- **claude-opus-5.5** — сильная LLM как судья (LLM-as-judge), 40 сценариев;
- **llama3.1:8b** — локальная LLM через Ollama, 40 сценариев (`python main.py judge-gold`).

Модель качества оценивается по out-of-fold прогнозам кросс-валидации: каждый сценарий оценивает модель, которая не видела его при обучении.

Каппа Коэна между разметчиком и метками генерации, в скобках ROC-AUC модели по меткам разметчика:

| Метрика | anna (15) | Claude (40) | llama (40) |
|---|---|---|---|
| Читаемость | 0.06 (0.43) | 0.22 (0.68) | 0.00 (—) |
| Чёткость целей | −0.18 (0.28) | 0.23 (0.36) | 0.00 (—) |
| Покрытие | 0.00 (—) | 0.23 (0.42) | 0.60 (0.73) |
| Согласованность | 0.02 (0.29) | 0.07 (0.44) | 0.38 (0.67) |

«—»: разметчик поставил всем сценариям одну оценку, и ROC-AUC не определён.

Каппа между разметчиками:

| Пара | Читаемость | Цель | Покрытие | Согласованность |
|---|---|---|---|---|
| anna ↔ Claude (15) | **0.38** | 0.06 | 0.00 | **0.25** |
| anna ↔ llama (15) | 0.00 | 0.00 | 0.00 | 0.02 |
| Claude ↔ llama (40) | 0.00 | 0.00 | 0.47 | 0.11 |

- **Человек не согласен с метками генерации:** каппа около 0 по всем метрикам. Из 15 сценариев 12 человек отклонил по согласованности, хотя генерация считала плохими только 4. Метки датасета — это то, что мы заказали у qwen, а не то, что она написала.
- **Покрытие человек оценил строже всех:** ни один сценарий не учитывает все ограничения требования (например, для пароля 8–64 нет значений 7, 8, 64 и 65). Рубрика «покрытие одного сценария» трактуется по-разному, это нужно уточнить в рубрике.
- **Ближе всего к человеку Claude** (каппа 0.38 и 0.25 по читаемости и согласованности). Llama ставит почти всем «хорошо» и с человеком не согласна.
- **Модель качества выучила метки генерации, а не мнение человека.** По меткам человека её ROC-AUC ниже 0.5. Высокий ROC-AUC на кросс-валидации (0.74–0.81) показывает, насколько хорошо модель воспроизводит метки генерации, а не реальное качество. 15 сценариев — маленькая выборка, но вывод совпадает с проверкой Claude на 40.
- **Что следует из этого.** Архитектура и обучение работают: модель обходит базовые модели на своих метках. Слабое место — данные. Первый пункт развития: разметить датасет заново, человеком или сильной LLM, которая ближе всего к человеку (Claude), и переобучить модель.

**Кейсы для REQ-01:** 30 кейсов, покрыто 24 из 24 обязательных проверок. Код исправил исходы граничных значений в 6 кейсах.

Формат `output/report.md` повторяет шаблон из ТЗ. Числа в шаблоне («10 / 8 / 2») — пример, поэтому в отчёте стоят наши фактические значения: 30 / 18 / 12. Кейсов 30, потому что одни только обязательные проверки дают 24 кейса: 4 поля × 6 проверок (пробелы, алфавит, спецсимволы, длина, XSS, SQL). К ним добавляются 6 свободных.

Ручная проверка нашла 4 кейса с ошибками в устройстве. Модель отметила неуспешными 12 кейсов, среди них все четыре:

| Кейс | Ошибка | Отмечен моделью |
|---|---|---|
| TC-002 | Две проверки в одном кейсе; в шаге «50 символов» у строки из 52 | да |
| TC-029 | Придумано правило «минимум 8 символов» для Имени | да |
| TC-030 | «Иванов Иван Иванович»: два пробела внутри, а ожидается успех | да |
| TC-026 | Название про пароль без заглавной буквы и цифры, а в шагах пустая строка | да |

На реальных кейсах это 4 найденных из 4 и 8 ложных тревог (TC-001, 006, 011, 012, 017, 018, 024, 025). Порог 0.60 строгий: модель предпочитает лишний раз отправить кейс человеку, чем пропустить ошибку. Выборка маленькая, это иллюстрация, а не измерение.

**История ошибок генератора.**

| Версия | Кейсов с логическими ошибками |
|---|---|
| Первая генерация | 11 из 29 |
| После вычисления исходов кодом | ~4 из 29 |
| После классификации свободных кейсов и отдельной проверки длины для маски | 4 из 30 |

В последней версии все 4 ошибки — в устройстве кейса, исход граничных значений везде верный.

Отчёт: `output/report.md`, данные: `output/results.json`, графики: `output/plots/`, история обучения: `output/training_metrics.json`.

## Ограничения

- **Анализатор требований.** На контрольном наборе из 9 требований (46 известных дефектов) он находит 48–52% дефектов (recall) по ручной проверке совпадений. Последний прогон после замены критерия на закрытый список дал 59% (27/46) по шаблонам ключа. Это один запуск без ручной проверки, а разброс между запусками ±2 дефекта на требование, поэтому улучшение не заявляем. Цель 70% на qwen2.5:7b не достигнута. Точность (precision) не измерялась, на хорошо описанном требовании большая часть находок — шум. Поэтому находки только подсказка автору, решение принимает человек.
- **Генератор.** Ошибки в устройстве кейса код не исправляет: несколько проверок в одном кейсе, придуманное правило в названии, шаги не совпадают с названием.
  - Исход «принимается» код ставит только в кейсах, которые проверяют формат значения: это обязательные кейсы и свободные кейсы, которые модель отнесла к формату. В остальных кейсах значение может отклоняться по другим правилам, например из-за уникальности.
  - Для поля с маской проверка длины — это «на одну цифру больше, чем вмещает маска». Строку из 1000 символов модель на таком поле зацикливала. Исход для лишней цифры — «не задано»: требование этого не описывает.
- **Метки датасета.** Это намерение при генерации, а не ручная разметка. Ручная разметка 15 сценариев и разметка Claude на 40 показали, что метки шумные: каппа с человеком около 0. Хорошие сценарии часто содержат противоречия, а заказанный недостаток появляется не всегда. Ручная разметка — 15 сценариев одного человека, это мало для точных цифр.
- **Язык генерации.** qwen2.5:7b изредка вставляет китайские иероглифы (требования DS-14, DS-16, DS-21). Код это не фильтрует.
