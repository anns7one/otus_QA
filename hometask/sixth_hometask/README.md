# Домашнее задание 6 — оптимизатор автотестов

## Что делает

Система читает автотесты (pytest, из ДЗ 3) и требования к API с приоритетами,
и выдаёт:

1. Тесты, сгруппированные по приоритету требования, которое они покрывают —
   от High к Low, плюс отдельная группа «без привязки к требованию».
2. Список дублирующих **шагов** между разными тестами (или «Не найдено»).
3. Список дублирующих/похожих **тестов** (или «Не найдено»).
4. Покрытие требований в процентах, включая непокрытые требования.
5. Оценку качества каждого теста (0-100) на основе читаемости и того,
   покрывает ли он хоть одно требование.

## Требования к окружению

- Python 3.11+ (используется общий `.venv` в корне репозитория)
- Ollama с моделью `qwen2.5:7b` (для LLM-судьи; без неё — режим `--no-llm`)
- Пакеты из `requirements.txt`: `sentence-transformers`, `openai`, `pytest`

## Установка

Из корня репозитория (`D:\Otus\otus_QA`):

```powershell
.\.venv\Scripts\python.exe -m pip install -r hometask\sixth_hometask\requirements.txt
```

## Запуск

Из папки `hometask\sixth_hometask`:

```powershell
cd hometask\sixth_hometask
python -m optimizer --tests suites/jsonplaceholder --requirements api_requirements.json
```

Пример полного вывода — [`example_report.md`](example_report.md) (сгенерирован
этой же командой).

Флаги:

- `--no-llm` — без эмбеддингов и LLM-судьи. Быстро и полностью
  детерминировано, но находит только **структурно точные** дубли тестов
  (полностью совпадающий набор шагов); семантические совпадения без
  идентичного кода без эмбеддингов не найти (см. «Ограничения»).
- `--out report.md` — сохранить отчёт в файл вместо печати в консоль.
- `--requirements <file>` — свой файл требований (по умолчанию
  `api_requirements.json`).

Автоматическая проверка самого оптимизатора на посеянном наборе с известным
правильным ответом (`ground_truth.json`):

```powershell
python -m pytest tests/ -v
```

## Архитектура: воронка, а не голые эмбеддинги

```
pytest-файлы -> AST-парсер -> тест = {сигнатура, шаги, docstring}
  |- дубли шагов:  нормализация (обезличивание имён переменных,
  |                 сортировка множеств) + сравнение по тексту
  |- дубли тестов: сигнатурный барьер -> Jaccard по шагам -> эмбеддинги ->
  |                 LLM-судья только для спорной средней зоны
  |- приоритет:    тест -> требование (метод+путь+статус+параметры,
  |                 точное совпадение) -> приоритет требования
  '- качество:     0.6*читаемость + 0.4*покрытие
                    читаемость = 0.5*эвристики + 0.5*LLM-рубрика
```

**Почему не просто эмбеддинги.** Проверила эмпирически на этом же наборе
тестов, каждая пара — реальный cosine (модель
`paraphrase-multilingual-MiniLM-L12-v2`):

| Пара | Дубль? | Cosine |
|---|---|---|
| `test_get_posts_list_returns_100_items` ↔ `test_get_all_posts_count` | да | 0.877 |
| `test_get_posts_list_returns_100_items` ↔ `test_get_posts_filtered_by_user_id` | **нет** (другое требование, другие параметры) | 0.891 |
| `test_get_posts_filtered_by_user_id` ↔ `test_update_post_with_put_returns_200` | нет (другой метод) | 0.826 |
| `test_create_post_returns_201_and_echoes_body` ↔ `test_update_post_with_put_returns_200` | нет (POST vs PUT) | 0.802 |

Голые эмбеддинги ставят не-дубли **выше** настоящего дубля — та же ошибка,
что в демо-ноутбуке курса (`Colab_embeddings_dubli_test_cases.ipynb`), где
TC-001↔TC-003 (успешный вход / неверный пароль, не дубль) получили 0.894, а
настоящий RU/EN-дубль TC-001↔TC-002 — только 0.664. Поэтому сначала —
сигнатурный барьер (метод, путь, статус, параметры должны совпасть точно),
и только внутри одной группы — сравнение по смыслу. Барьер отсекает все три
ложные пары из таблицы выше **до** вызова эмбеддингов.

**Почему требование с параметрами не совпадает с требованием без них.**
`GET /posts` (весь список, REQ-01) и `GET /posts?userId=1` (отфильтрованный,
REQ-04) — разные проверки с одинаковым методом/путём/статусом. Сопоставление
тест → требование сравнивает набор параметров точно, а не только
метод+путь+статус — иначе оба требования покрывались бы одним тестом.

## «Обучение» из ТЗ

Формально fine-tuning модели не проводился — использованы предобученные
`paraphrase-multilingual-MiniLM-L12-v2` (эмбеддинги) и `qwen2.5:7b` через
Ollama (судья). «Обучением» здесь является калибровка порогов и правил на
размеченных данных (`ground_truth.json`, посеянные дубли с известным
ответом) — `tests/test_optimizer.py` формально проверяет, что пороги
(Jaccard=1.0 для точных дублей, cosine≥0.80 для похожих, барьер по сигнатуре)
дают правильный результат на этом наборе.

## Ограничения и что добавить в production

- **`--no-llm` не находит семантические дубли без идентичного кода.**
  Пара с cosine 0.877 (реальный дубль) требует эмбеддингов; структурный
  Jaccard для неё — всего 0.25 (разные способы проверки одного и того же:
  через цикл с проверкой схемы против простого `len(...) == 100`).
- **Нормализация шагов не разворачивает промежуточные переменные.**
  `body = response.json(); len(body)` и `len(response.json())` — по смыслу
  одно и то же, но нормализуются в разные строки (`len(VAR)` против
  `len(VAR.json())`), потому что нормализация работает на уровне AST одного
  выражения, а не датафлоу между строками. Эмбеддинги на уровне docstring +
  шагов частично это компенсируют.
- **Список "keep names" при обезличивании — эвристика.** `len`, `isinstance`,
  `int`, `str` и похожие сохраняются как значимые; всё остальное считается
  переменной. Нетипичное использование этих имён как переменных (`int = 5`)
  дало бы неверную нормализацию — в тестах API такое не встречается, но это
  не проверяется явно.
- **LLM-судья не детерминирован между запросами Ollama**, хотя
  `temperature=0` снижает разброс. Для критичных решений (например, удалить
  ли тест как дубль) стоит требовать согласия нескольких прогонов, а не
  доверять одному ответу.
- **Требование `parse.py` — прямые вызовы `requests.*`.** Хелперы,
  фикстуры и сложную параметризацию тестов система не разбирает; такие
  тесты не получат сигнатуру и попадут в «без привязки к требованию».
- **Правило фильтрации тривиальных шагов** (`assert x.status_code == N`
  один, без другого совпадающего шага в паре) — единственное жёстко заданное
  исключение. Другие виды шума (например, единичный `assert response is not
  None`) не отсекаются отдельно.
