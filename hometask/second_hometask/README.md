# ДЗ-2. Генерация тестовой документации моделью

Доработка модели из первого домашнего задания: теперь она обучается на
предметном корпусе и генерирует четыре документа по странице
**https://otus.ru/catalog/courses?categories=programming**

| Документ | Файл |
|---|---|
| 3 тест-кейса (один негативный) | [output/test-cases.md](output/test-cases.md) |
| Чек-лист проверки страницы | [output/checklist.md](output/checklist.md) |
| Тест-план по бизнес-требованиям | [output/test-plan.md](output/test-plan.md) |
| Отчёт о тестировании (1 упал, 2 прошли) | [output/test-report.md](output/test-report.md) |

Бизнес-требования (придуманы самостоятельно):
[requirements/business-requirements.md](requirements/business-requirements.md)

## Запуск

```bash
pip install -r requirements.txt
python generate.py                    # авто: Ollama если доступна, иначе n-gram
python generate.py --backend ngram    # только обученная n-gram модель, без Ollama
python generate.py --backend ollama   # локальная LLM llama3.2
python model.py                       # самопроверка модели
```

Для бэкенда `ollama` нужна запущенная Ollama с моделью `llama3.2`:
```bash
ollama pull llama3.2
```

## Что доработано в модели

Исходная `TestLLM` из ДЗ-1 считала частоты пар «слово → следующее слово» и умела
предсказывать одно слово. `DocGeneratorLLM` (файл `model.py`) добавляет:

1. **n-граммы произвольного порядка** — не только биграммы, но и триграммы
   (`order=3` по умолчанию): контекст из нескольких слов даёт более осмысленные
   продолжения;
2. **`generate(seed, length)`** — генерация цепочки слов, а не одного;
3. **`stats()`** — что модель выучила: размер словаря, число контекстов и
   переходов. Печатается при каждом запуске как доказательство обучения.

Обучающий корпус (`corpus.py`) — 48 предметных формулировок из тестовой
документации вместо 10 предложений про кота: шаги тест-кейсов, пункты
чек-листа, разделы тест-плана, формулировки отчёта.

## Архитектура

```
results.json ──┐
               ├─► generate.py ──► backend.render() ──► output/*.md
page_context ──┤                        │
business-req ──┘                        ├── OllamaBackend  (llama3.2)
                                        └── NgramBackend   (DocGeneratorLLM)
                                                 │
                                        шлюз качества ──► предупреждения
```

**Два бэкенда — честно о разнице.** Биграммная модель обучается, но связного
текста статистика частот дать не может: `NgramBackend` собирает документ по
шаблону, а формулировки достраивает обученная модель. `OllamaBackend`
использует локальную LLM и даёт читаемый текст. Оба пишут одни и те же четыре
файла, выбор — флагом `--backend`.

## Разделение труда: код гарантирует, модель интерпретирует

Главный принцип, заложенный в генератор:

| Делает КОД (детерминированно) | Делает МОДЕЛЬ |
|---|---|
| считает passed/failed из `results.json` | формулирует оценку остаточного риска |
| рендерит сводку, таблицу результатов, дефекты, покрытие | пишет тест-кейсы, чек-лист, тест-план |
| **выносит вердикт go/no-go по порогам severity** | обосновывает вердикт словами |
| проверяет результат в шлюзе качества | — |

Поэтому в отчёте физически не может появиться выдуманная цифра или
противоречивый вывод: числа и вердикт модель не формирует, а получает.

## Шлюз качества

После генерации `generate.py` проверяет результат и печатает предупреждения:

- ровно 3 тест-кейса, среди них есть негативный, у каждого есть блок «Шаги»;
- числа в отчёте совпадают с `results.json`;
- в отчёте нет выдуманных идентификаторов (TC/BR/BUG, которых нет в фактах);
- присутствуют разделы «Оценка остаточного риска» и «Вывод о релизе»;
- вывод о релизе совпадает с вердиктом, рассчитанным по порогам severity;
- текст модели не съехал в транслитерацию.

Если модель не вернула нужные разделы, делается **одна повторная попытка с
конкретным фидбеком** — что именно было не так.

## Наблюдения по ходу работы

Малая модель (llama3.2, 3B) на первых прогонах:

- пропускала шаги в тест-кейсах → вылечилось строгим шаблоном вывода в промпте;
- писала транслитом («dogruzhait kartinki») → вылечилось явным требованием
  писать кириллицей + проверкой в шлюзе;
- ломала многоколоночные markdown-таблицы → таблицы фактов забрал код;
- игнорировала «напиши только два раздела» → нужные разделы извлекаются из
  ответа кодом, при отсутствии — ретрай с фидбеком;
- написала «релиз разрешён» при упавшем кейсе с Major-дефектом (optimism bias)
  → вердикт стал считаться кодом по порогам.

Вывод: чем больше гарантий берёт на себя код, тем меньше остаётся места для
галлюцинаций модели. Схемная валидация при этом не ловит смысловые ошибки —
противоречивый вывод о релизе прошёл проверку чисел и потребовал отдельного
правила.
