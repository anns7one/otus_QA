# REQ-01 - Форма регистрации

Форма принимает поля: Имя, E-mail, Телефон, Пароль, согласие с политикой
конфиденциальности, кнопку «Зарегистрироваться», кнопку перехода к авторизации, кнопку перехода к восстановлению пароля.

- **Имя.** Обязательно для заполнения. Принимает на вход только буквы до 50 символов.
- **E-mail.** Обязательно для заполнения. Валидация: содержит символ `@`,
  значение введено латиницей или цифрами. Проходит проверку на уникальность: если в базе уже есть пользователь с таким email — ошибка «Пользователь с таким email уже существует, авторизуйтесь на сайте».
- **Телефон.** Обязательно для заполнения. Маска: `+7(...)...-..-..`.
  Проходит проверку на уникальность: если в базе уже есть пользователь с
  таким номером — ошибка «Пользователь с таким номером телефона уже
  существует, авторизуйтесь на сайте».
- **Пароль.** Обязательно для заполнения.От 8 до 64 символов, минимум одна цифра и одна заглавная буква.Допустимые символы: цифры, латинские буквы,знаки препинания.
- **Согласие с политикой конфиденциальности.** Обязательный чекбокс по умолчанию должен быть активен

## Поведение

- Если незаполненных обязательных полей ≥ 1 - регистрация не происходит, появляется текст «Заполните обязательные поля» (или подсветка пустых
  полей, в зависимости от дизайна).
- Если все обязательные поля заполнены и валидны - пользователь
  регистрируется.
- После успешной регистрации - поп-ап с подтверждением, пользователь
  остаётся на той же странице, где был открыт поп-ап регистрации.
- Система авторизует пользователя сразу после успешной регистрации.


Техника: Структурируй план по ISO/IEC/IEEE 29119-3: объём тестирования, подход/стратегия, критерии входа/выхода, риски, ресурсы.

Формат: Верни тест-план с разделами: Объём, Подход, Критерии входа, Критерии выхода, Риски, Ресурсы.

Ограничения: Пиши на русском. Не придумывай требований, которых нет в тексте выше.

## Сгенерированный документ
```
### Тест-план

#### Объём
Тестирование будет охватывать все функциональные требования формы регистрации, включая проверку всех полей и их валидацию.

#### Подход/стратегия
Подход к тестированию будет основан на методики черного ящика (black-box testing), где внимание будет сосредоточено на поведении системы при различных входных данных. Также будут применены методы белого ящика (white-box testing) для проверки внутренней структуры и логики программы.

#### Критерии входа
- Система должна быть полностью развернута и готова к тестированию.
- Все необходимые документы и требования должны быть предоставлены.
- Участники тестирования должны быть подготовлены и осведомлены о целях и методах тестирования.

#### Критерии выхода
- Все функциональные требования формы регистрации должны быть полностью удовлетворены.
- Не должно быть критических дефектов, которые могут повлиять на работу системы.
- Отчет по тестированию должен содержать все найденные проблемы и рекомендации по их устранению.

#### Риски
1. **Недостаточная валидация данных**: Возможно, не все входные данные будут корректно проверены.
2. **Проблемы с уникальностью данных**: Возможны ошибки при проверке уникальности email и телефонных номеров.
3. **Неудачное отображение сообщений об ошибках**: Сообщения могут быть некорректными или не соответствовать требованиям.
4. **Неправильная авторизация после регистрации**: После успешной регистрации пользователь может не быть автоматически авторизован.

#### Ресурсы
- Тестировщики: минимум 2 специалиста для параллельного тестирования.
- Инструменты тестирования: Selenium, Postman или аналогичные.
- Доступ к базе данных для проверки уникальности email и телефонных номеров.
- Платформа для отчетности: Jira, TestRail или аналогичная.

### Подробный план тестирования

#### Тест-кейсы
1. **Тестирование обязательного заполнения полей**
   - Проверка на наличие текста «Заполните обязательные поля» при незаполненных обязательных полях.
2. **Валидация имени**
   - Ввод букв до 50 символов: Успешная регистрация.
   - Ввод более 50 символов: Ошибка валидации.
3. **Валидация E-mail**
   - Правильный формат email с символом @ и латиницей/цифрами: Успешная регистрация.
   - Неправильный формат email (например, без символа @): Ошибка валидации.
   - Email уже существует в базе данных: Сообщение об ошибке «Пользователь с таким email уже существует».
4. **Валидация телефона**
   - Правильная маска +7(...)...-..-..: Успешная регистрация.
   - Неправильная маска: Ошибка валидации.
   - Телефон уже существует в базе данных: Сообщение об ошибке «Пользователь с таким номером телефона уже существует».
5. **Валидация пароля**
   - Пароль от 8 до 64 символов, минимум одна цифра и одна заглавная буква: Успешная регистрация.
   - Неверный формат пароля (например, без цифр или заглавных букв): Ошибка валидации.
6. **Проверка согласия с политикой конфиденциальности**
   - Пустая галочка: Ошибка «Необходимо согласиться с политикой конфиденциальности».
7. **Успешная регистрация**
   - Все поля заполнены и валидны: Успешная регистрация, появление поп-апа с подтверждением.

#### Отчетность
Отчет будет содержать:
- Список выполненных тест-кейсов.
- Описание найденных дефектов с приоритетами (критические, высокие, средние, низкие).
- Рекомендации по устранению выявленных проблем.

### Заключение
Тестирование формы регистрации будет выполнено в соответствии с вышеуказанным планом. Все найденные проблемы будут учтены и исправлены перед запуском системы в production.
```

| contextuality | 5 | Тест-план точно опирается на требование и не содержит условий, которых нет в исходном требовании. |

| scenario_coverage | 3 | Покрыты основные позитивные и негативные случаи, но могут быть добавлены дополнительные сценарии для полноты тестирования. |
| unambiguity | 4 | Формулировки в целом ясны, но некоторые термины могут быть определены более точно для исключения двусмысленности. |

| consistency | 5 | Все пункты документа согласованы и не противоречат друг другу. |
| correctness | 4 | Значения и условия в документе соответствуют требованиям, но могут быть уточнены для полной точности. |
