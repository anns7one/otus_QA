# Результат: qa_report

## Промпт
```
Ты QA lead, готовящий отчёт по итогам тестирования.

Контекст (требование):
# REQ-01 - Форма регистрации

Форма принимает поля: Имя, E-mail, Телефон, Пароль, согласие с политикой
конфиденциальности, кнопку «Зарегистрироваться», кнопку перехода к авторизации, кнопку перехода к восстановлению пароля.

- **Имя.** Обязательно для заполнения. Принимает на вход только буквы до 50 символов.
- **E-mail.** Обязательно для заполнения. Валидация: содержит символ `@`,
  значение введено латиницей или цифрами. Проходит проверку на уникальность: если в базе уже есть пользователь с таким email — ошибка «Пользователь с таким email уже существует, авторизуйтесь на сайте».
- **Телефон.** Обязательно для заполнения. Маска: `+7(...)...-..-..`.
  Проходит проверку на уникальность: если в базе уже есть пользователь с
  таким номером — ошибка «Пользователь с таким номером телефона уже
  существует, авторизуйтесь на сайте».
- **Пароль.** Обязательно для заполнения.От 8 до 64 символов, минимум одна цифра и одна заглавная буква.Допустимые символы: цифры, латинские буквы,знаки препинания.
- **Согласие с политикой конфиденциальности.** Обязательный чекбокс по умолчанию должен быть активен

## Поведение

- Если незаполненных обязательных полей ≥ 1 - регистрация не происходит, появляется текст «Заполните обязательные поля» (или подсветка пустых
  полей, в зависимости от дизайна).
- Если все обязательные поля заполнены и валидны - пользователь
  регистрируется.
- После успешной регистрации - поп-ап с подтверждением, пользователь
  остаётся на той же странице, где был открыт поп-ап регистрации.
- Система авторизует пользователя сразу после успешной регистрации.


Техника: Реального прогона тестов не было. Подготовь ЗАПОЛНЯЕМЫЙ ШАБЛОН отчёта по структуре Test Completion Report (ISO 29119-3), а не выдуманный результат.

Формат: Верни шаблон с разделами:
1. Цель и область тестирования — перечисли КОНКРЕТНЫЕ правила валидации из требования (не только названия полей, а точные условия: длины, маски, обязательность, проверки на уникальность). Это НЕ плейсхолдер.
2. Итоги — плейсхолдер [заполнить после прогона].
3. Дефекты по severity — плейсхолдер [заполнить после прогона].
4. Метрики покрытия — плейсхолдер [заполнить после прогона].
5. Рекомендация (go/no-go) — плейсхолдер [заполнить после прогона].

Ограничения: Пиши на русском. Запрещено указывать конкретные числа результатов — только плейсхолдеры (кроме раздела «Цель»).
```

## Оценка
| Критерий | Балл | Комментарий |
|---|---|---|
| readability | 4 | Структура документа понятна, но есть небольшие недочеты в формулировке. |
| contextuality | 5 | Документ точно отражает требование и не содержит лишних условий. |
| goal_clarity | 4 | Цели проверки понятны, но некоторые моменты могут быть раскрыты более детально. |
| scenario_coverage | 3 | При описании поведения формы отсутствуют негативные и граничные случаи. |
| unambiguity | 4 | Формулировки в целом ясны, но некоторые термины могут быть более точно определены. |
| atomicity | 5 | Каждый пункт документа описывает одну проверяемую вещь. |
| singularity | 4 | Нет явных дублирующих пунктов, но некоторые моменты могут быть объединены для улучшения читаемости. |
| consistency | 5 | Все значения и условия согласованы с требованием. |
| correctness | 4 | Значения и условия совпадают с требованиями, но есть небольшие недочеты в формулировке. |
