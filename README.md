# AI в QA: практические проекты

Проекты по применению AI в тестировании: генерация тестовой документации и автотестов, RAG, тестирование безопасности LLM-агентов, анализ набора автотестов.
Все проекты работают на **локальных open-source моделях через Ollama** данные не уходят во внешние сервисы.

Проекты выполнены в рамках курса OTUS, 2026.

## Подробнее

### 1. Предсказание следующего слова

- Обучение биграммной модели: для каждого слова подсчитывается, какие слова и как часто идут за ним.
- Предсказание — самое частое продолжение. Простейшая иллюстрация принципа, на котором строятся языковые модели.

### 2. Генератор тестовой документации

- **Своя нейросеть на PyTorch:** эмбеддинги, self-attention с маской будущих токенов, обучение на фразах из QA-домена с выводом loss по эпохам, генерация текста.
- **Пайплайн документации:** скрипт скачивает страницу каталога, разбирает её на фильтры, кнопки и карточки; модель описывает страницу, формулирует бизнес-требования и пишет чек-лист, тест-кейсы, тест-план и отчёт о тестировании.
- **Контроль качества генерации:** структурированный вход вместо «сплошного» текста страницы, образцы хорошего и плохого результата в промптах, temperature 0.2. Таблицу результатов в отчёте строит код — модель не может выдумать тест-кейс или цифру.
- **Человек в контуре:** документы сохраняются только после подтверждения.

### 3. Генерация API-автотестов

- Модель `qwen2.5-coder:7b` в Docker-контейнере получает [спецификацию API](hometask/third_hometask/api_spec.md) и [промпт](hometask/third_hometask/prompt.md) и пишет готовый к запуску файл с тестами.
- Промпт построен по схеме «Роль → Контекст → Задача → Формат → Ограничения» и хранится в репозитории как код (prompt-as-code).
- Учтена особенность тестового API: запись данных имитируется, поэтому тесты проверяют **контракт ответа** (код, структуру, содержимое), а не сохранение. Такие ловушки явно описаны в спецификации для модели.
- Результат — [tests/test_jsonplaceholder.py](hometask/third_hometask/tests/test_jsonplaceholder.py): 3 теста, включая негативный.

### 4. Локальный RAG

- **База знаний:** 10 текстов по теории тестирования, сгенерированных по фрагментам ISTQB Foundation Level Syllabus v4.0; каждый текст проверяется и при необходимости корректируется человеком.
- **Поиск:** эмбеддинги `nomic-embed-text` + косинусная близость, top-4 документа.
- **Генерация:** ответ строится только по найденному контексту; на вопрос вне базы система честно отвечает, что информации нет — см. [пример диалога](hometask/fourth_hometask/example_dialog.md).
- Без внешних Python-зависимостей — только стандартная библиотека.

### 5. Тестирование безопасности LLM-агента

- Агент на FastAPI с инструментами `run_sql` (база с клиентами, заказами и секретами) и `search_documents` — в двух версиях: уязвимой и защищённой.
- **Red teaming** по 6 классам атак: prompt injection, утечка системного промпта, tool abuse, RAG poisoning, обфускация (base64 / ROT13 / leetspeak), jailbreak — с привязкой к OWASP GenAI LLM Top 10.
- **Защита:** Input Guard, Output Guard с канареечным токеном, least privilege для SQL (только `SELECT`, без доступа к таблице секретов), изоляция пользовательского ввода в промпте, карантин документов с инъекциями, лимит итераций вызова инструментов.
- **Автотесты:** 19 payload'ов (16 атак + 3 контрольных легитимных запроса) — [19/19 passed](hometask/fifth_hometask/tests/security_test_report.md), отчёт генерируется автоматически.
- Результаты «до / после» и ограничения решения — в [REPORT.md](hometask/fifth_hometask/REPORT.md).

### 6. Оптимизатор автотестов

- Разбирает pytest-тесты через AST: шаги и сигнатура запроса (метод, путь, статус, параметры).
- **Дубли шагов** — после нормализации (обезличивание переменных). **Дубли тестов** — воронкой: сигнатурный барьер → Jaccard по шагам → эмбеддинги → LLM-судья только для спорных пар.
- Сопоставляет тесты с требованиями, группирует по приоритету, считает покрытие (в том числе взвешенное по приоритетам) и оценивает качество каждого теста.
- Эмпирически показано, что «голые» эмбеддинги ставят не-дубль выше настоящего дубля (cosine 0.891 против 0.877), — поэтому сначала сигнатурный барьер, потом сравнение по смыслу.
- Корректность самого инструмента проверяется тестами на эталонной разметке ([ground_truth.json](hometask/sixth_hometask/ground_truth.json)); есть быстрый детерминированный режим `--no-llm`.
- [Пример отчёта](hometask/sixth_hometask/example_report.md).

## Подход

- **Локальные модели.** Всё работает через Ollama на своей машине — подходит для данных, которые нельзя отправлять во внешние API.
- **Контроль галлюцинаций.** Структурированный вход, образцы в промптах, низкая температура, ответ только по контексту; факты и числа считает код, а не модель.
- **Человек в контуре.** Сгенерированное сохраняется только после подтверждения, результат можно скорректировать.
- **AI-инструменты тоже тестируются.** Эталонная разметка для оптимизатора, автотесты безопасности для агента.
- **Честные ограничения.** В проектах 4–6 описано, где решение не справится и что нужно добавить для продакшена.

## Как запустить

Нужны Python 3.11+, Docker и [Ollama](https://ollama.com).

| Проект | Запуск |
|---|---|
| 1 | `python hometask/first_hometask.py` |
| 2 | `pip install torch ollama`, `ollama pull llama3.2`, затем `python hometask/second_hometask/second_hometask.py` |
| 3 | В папке проекта: `docker compose up -d`, `docker exec ollama-hw3 ollama pull qwen2.5-coder:7b`, `python generate_tests.py`, `pytest tests/ -v` |
| 4–6 | См. README в папке проекта: [4](hometask/fourth_hometask/README.md), [5](hometask/fifth_hometask/README.md), [6](hometask/sixth_hometask/README.md) |
